## TL;DR

1. **Every patient-facing rule is enforced in our Node backend against our Postgres, keyed off `subscriptions` rows + Cognito groups; Semble has no concept of any of it.** The load-bearing gates are: *paid-up* (`findEntitlingSubscription`: an `active` row whose `current_period_end >= now-72h`, BE:`utils/entitlement.ts:34-52`), *role entitlement* (Cognito groups minted from `roles_products` for the Stripe price, BE:`services/roles.service.ts:15-39`), *intake survey done* (BE:`services/activities.service.ts:262-276`), *weight fresher than 45 days for Doctor* (BE:`activities.service.ts:290-304`), *no pending appointment for that role* (`:334-350`), *first/follow-up consultation type* (`:413-458`), *tier cooldown* (`:482-525`, `:642-777`), *90-day programme windows + allocation* (`:379-410`, `:1649-1723`), *2-hour lead time on book/reschedule/cancel*, and *€89 prescription window of 30 days* (BE:`services/tierJourney.service.ts:390-409`).
2. **Two things Art already decided change the rule set for new patients**: (a) the intake questionnaire gates **joining** (video token), not booking, and only for sign-ups on/after **2026-08-24** (PROD-ENV L411-412; BE:`services/dailyVideo.service.ts:377-390`); (b) the failed-payment **attendance gate is deployed but OFF on prod** (`ATTENDANCE_GATE_ENFORCE_FROM` absent from PROD-ENV; kill-switch semantics BE:`config/index.ts:203`).
3. **The €89 funnel still auto-books the first doctor consult on prod.** The backend saga claims a slot and writes the `calendar_events` row inside the registration transaction (BE:`services/registerWithPayment.service.ts:657-711`); the FE change that stops this (`beyondbmi-front-end` `79f60ab` "the €89 consult no longer books an appointment at payment") is on FE `origin/qa` only, **not** FE `origin/master` (verified by `git merge-base`).
4. **Plan state is a server-derived stage machine, not a Stripe status**: `none → consult_paid → consult_booked → consult_done → ninety_day_active → ninety_day_overdue → ninety_day_completed`, plus `legacy_member` / `legacy_lapsed` (BE:`tierJourney.service.ts:35-44`, `164-374`). One-time purchases (€89, €399, comps) are stored as *synthetic* `subscriptions` rows whose `stripe_subscription_id` is a `pi_…`/`pi_comp_…` id and which **no Stripe webhook can ever close** — only `current_period_end` ends them (BE:`tierJourney.service.ts:104-113`; `utils/entitlement.ts:26-31`).
5. **Prescriptions**: the doctor authors a draft in our staff portal (PDF → S3), the **patient** chooses the pharmacy and triggers the send: ROI = SendGrid email to a whitelisted pharmacy/`@healthmail.ie` domain (`status → processed`), NI = SignatureRX e-prescription (`status → delivered`, `srx_status` from webhooks) (BE:`services/prescription.service.ts:224-269`; `services/signaturerx.service.ts:135-227`). **Semble's API can *read* a prescription and hand back its PDF but has no mutation to create or send one** (MEM:`reference_adhd_semble_backend.md` §"PRESCRIPTIONS via the Semble API — SETTLED Sep 9"). So with Semble as the record, the doctor prescribes *in Semble*, and **our portal owns delivery** (pharmacy choice, Healthmail email, SignatureRX, audit log) unless BBMI adopts Semble's own share-to-contact flow.
6. **Recommended split (§7):** Stripe stays the biller; **our portal backend keeps every entitlement / eligibility / cooldown / weight / survey / override rule** (nothing in Semble can express them — MEM:`project_bbmi_semble_implementation.md`; JM lines 320-323 assume Semble booking but Semble has no per-patient rules engine); **Semble owns** patient demographics, the appointment record (single calendar; replaces Cronofy + `calendar_available_times`), clinical notes, questionnaires (if the API exposes them — unverified), documents, the prescription artifact, invoices for ad-hoc items, and patient comms it can send natively. Identity stays **Cognito-sub-as-primary-key with a new `semble_patient_id` mapping** — do not make the Semble ObjectId the login identity (§8).
7. **Two rule divergences to raise with the client** before design freezes: the journey map says MDT spacing is "±7 days of each monthly target" (JM:322, 333) but code implements *earliest-date windows only* (`NINETY_DAY_SCHEDULE` + a 4-week booking window, BE:`config/index.ts:245-250`, `services/availability.service.ts:693-698`); and the map introduces a **Pure Pharmacy delivered-to-door option** (JM:351-353, 492-495) that has no code today.

## 7. Recommended owner per rule — reasoning

**Principle:** Semble is the *clinical* system of record (patients, bookings, notes, documents, prescriptions, invoices). It is **not** a commerce or entitlement engine: no recurring billing, no per-patient booking policies, no cooldown/weight/survey gates, no overrides, no concept of tier stage (KB prep doc:57-72; MEM:`project_bbmi_semble_implementation.md`). Its API has no `createdBy`/cancellation metadata on bookings, rate-limits via "too often" GraphQL errors, paginates with duplicates, has webhooks whose event types are undocumented, and returns Dublin wall-clock times tagged `Z` (MEM:`reference_adhd_semble_backend.md` §hard facts, §prescriptions). Therefore:

1. **STRIPE keeps money; PORTAL keeps entitlement.** R7-R9, R12, R15-R20, R22: reproduce `findEntitlingSubscription` + the tier stage machine in the new backend (they are already pure functions of `subscriptions` + doctor bookings). Replace Cognito-group side effects with a computed entitlement (`roles` per plan from versioned config) and, if the FE still needs groups, treat them as a cache refreshed from that computation (fixes R6's stale-`community` class). Keep the synthetic-row pattern (`pi_` entitlements with explicit `current_period_end`) — it is the only thing that makes one-time purchases expire.
2. **PORTAL keeps every booking rule (R23-R36, R33 windows)** and evaluates it against **Semble bookings** rather than our calendar tables: sequence/first-vs-follow-up from Semble product + booking history; pending-per-role from Semble bookings by product; cooldown from the last completed Semble booking's end; 90-day allocation from bookings-since-programme-start by product. Availability shown to the patient = Semble `availabilities` filtered by our window/floor (R29-R34) — Semble cannot apply per-patient policy itself. The 2-hour lead time and the hold/claim semantics (R14, R35) must be re-implemented: Semble has no hold; ADHD Now's booking API mitigates races with duplicate/overlap guards and cancels the loser (MEM:`reference_adhd_semble_backend.md` §ADHDsemble). **Decision needed**: whether MDT spacing is "earliest date" (code) or "±7 days" (JM:322).
3. **SEMBLE owns the appointment record and clinician roster** (product/type, duration, clinician role, availability, cancellations). This retires Cronofy, `calendar_available_times`, the slot sweepers, reassignment tooling and the drift class in KB:`03:§3-5`. But the portal must persist its own **booking index** (Semble booking id, product, patient, start/end, status, created-by-portal flag) because Semble deletes on cancellation and exposes no `createdBy` — audit and no-show/cancel semantics (R28, R36) need our copy. **Attendance status** (`completed`/`noshow`) must be sourced from Semble (booking status / consultation) rather than a doctor pressing our button — confirm which Semble field carries "attended".
4. **Join gates (R37-R39) stay PORTAL.** They are policy on top of a video session; whether the session is Semble video or Daily is a product decision. Keep the two env kill-switches and the fail-open stance.
5. **Surveys**: the *rule* (R25, R37, R41-R43) stays PORTAL; the *data* should move to Semble questionnaires **only if** the API can (a) create/complete a questionnaire for a patient from our portal and (b) read completion — unverified. If not, Tally → portal stays and a PDF/summary is pushed to Semble as a document.
6. **Prescriptions**: SEMBLE authors and stores (R44, R46 become "show only signed/shared prescriptions read via `prescriptions(dateRange)`/`pdfDownloadUrl`"); PORTAL owns R45 (window), R47-R52 (delivery: pharmacy choice, Healthmail email with the Semble PDF, SignatureRX for NI, audit log, one-send rule, admin reset). Rationale: Semble has **no create/send prescription mutation**, `sendEmail` cannot attach a file, Semble has never sent to `@healthmail.ie` (untested), and Irish e-prescribing has no Healthmail API (MEM:`reference_healthmail_integration.md`). The delivered-to-door option (JM:351) is a new PORTAL flow. Retire the McKeevers Lambda (R52) into the portal's SRX path.
7. **Measurements (R53-R56) stay PORTAL.** Weight is patient-entered, high-frequency, and gates booking; keep the append-only + log model and the effective-date rule. Push a periodic summary (or each weigh-in) to Semble only if an observations API exists [unverified].
8. **Identity (R1-R2, R10-R11)**: PORTAL/Cognito — see §8.
9. **CRM (R22)**: unchanged writers, but the Semble patient id should be stored on the HubSpot contact as the contract requires (KB prep doc:47) — the portal is the natural writer since it knows both ids.

## 8. Identity model today, and what changes when Semble holds the patient record

**Today**
- `patients.id` **is** the Cognito `sub` (uuid PK, `@PrimaryColumn`), set by the PreSignUp Lambda `preSignUpUser`, which POSTs `{id=event.userName, …}` to `/api/v1/user/` — it does not auto-confirm and hard-requires `clientMetadata.gender/dob/acceptTerms` (KB:`05c:125-162`; BE:`entities/patients.entity.ts:26-28`; `patients.service.ts:526-620`). There is now also a nullable `patients.cognito_sub` mirror column, written by the funnel saga (BE:`entities/patients.entity.ts:99-100`; `registerWithPayment.service.ts:646`), but nothing reads it as the key.
- Both pools use **email as username**, so `sub == username`; that is why `AdminGetUser(Username: sub)` works (BE:`cognitoAdmin.service.ts:145-167`).
- Because the PK is the sub, **re-registration = PK migration across 19 hard-coded child tables** in a 60-s transaction, with Stripe metadata repointed best-effort afterwards (BE:`patients.service.ts:333-459`; KB:`03:§6`). Missing tables keep the old id forever (KB:`03:282`).
- Email change must be done Cognito → Stripe → DB with one-deep rollback (KB:`03:§7`).
- Stripe ↔ patient link = `stripe_accounts.stripe_customer_id` (PK) ↔ `patient_id` (unique); self-heals **by email** when a returning member checks out as a new Stripe customer (BE:`payment.service.ts:134-199`).
- HubSpot is keyed by **email**; SignatureRX by our `prescription.id` (`external_id`) and raw patient fields (never `patients.srx_customer_id`, which is dead — KB:`03:367-368`).

**With Semble as the clinical record**
- Semble patients have a GraphQL ObjectId (24-hex) **and** a staff-facing "System" number in `Patient.numbers[]`; `patients(search:)` is fuzzy (27 hits for "Joseph") and Semble has no patient login/SSO (MEM:`reference_adhd_semble_backend.md` §PATIENT ID GOTCHA, §comms). So the Semble id **cannot** be the login identity, and search-by-name/email cannot be the linkage.
- Recommended model: keep **Cognito `sub` as the portal's stable patient key** (as an ordinary uuid column, no longer *the* PK that must be migrated — give the portal row its own immutable id), add `semble_patient_id` (ObjectId) + `semble_system_number`, and make the link **explicit and one-to-one** in a mapping table with provenance (created-by-portal vs matched-by-import). Store the portal id / Cognito sub on the Semble patient if a custom field or `numbers[]` entry is writable [unverified — open question], else keep the mapping portal-side only.
- Provisioning order for a new patient becomes: Cognito user → portal row → **Semble `createPatient`** (idempotent on our id) → Stripe customer (metadata `patientId`). Failure between steps must be reconciled by a job, not by a PreSignUp trigger that blocks sign-up on a downstream outage (KB:`05c:157-162`).
- Re-registration/reactivation should become "reattach the Cognito user to the existing portal row" (no PK migration); the Semble record is unaffected because it is linked by the portal id, not the sub.
- Email change: Cognito (login) + Stripe (billing) + HubSpot (key!) + Semble (comms) — four systems; HubSpot's email-as-key makes a rename a merge. Semble consent flags (`communicationPreferences.receiveEmail`) must be honoured before any portal-triggered Semble email.
- Migration note (contract): Semble will not extract from our system; "dataset" definition drives cost (€3k vs €15k) (MEM:`project_bbmi_semble_implementation.md`). ~10,081 patient rows exist (KB:`06:932`); only ~970 had an active subscription on 17 Aug and 175 of those have no intake survey (BE:`config/index.ts:186-188`) — decide whether lapsed patients are migrated to Semble at all.
- Staff identity: `doctors.id` = staff-pool sub, clinical role from `doctors.role`, admin from the Cognito `admin` group (KB:`01:587-603`). With Semble, clinician role/registration comes from Semble `User`; the staff portal is likely replaced, but the portal backend still needs a staff identity for admin overrides/resets (R24, R51).

## 9. Implications for the new portal

**Must-have**
- One server-side `evaluate(patient)` returning: tier stage, entitlement (paid-up incl. 72h grace), roles, per-role `canBook{reason, earliestDate, allocation}`, `canJoin(booking)`, `canSendRx(prescription)` — consumed by UI, availability and every mutation. No FE-decided eligibility (already the tier-journey doctrine, BE:`tierJourney.service.ts:114-115`).
- Persist synthetic entitlement rows for one-time purchases with explicit `current_period_end`; supersede on real subscription; 72h renewal grace for `sub_` only; `payment_paused` derived from `pause_collection`.
- Idempotent Stripe webhook handling keyed on `event.id` + `stripe_subscription_id` unique index; entitlement recomputed from the row, never from webhook side effects.
- Rule config as versioned data: role sets per price, cooldown months per role/plan, `NINETY_DAY_SCHEDULE`, allocation, gate cutoff dates, E89 doctor list, weight threshold, Rx window days, pharmacy directory.
- Booking index mirroring Semble bookings (id, product, clinician, patient, start/end, status, source, cancelled/no-show flags) — Semble deletes cancellations and has no `createdBy`.
- Overrides table + admin audit (R24, R31, R51) retained.
- Weights/BP/height store with effective-date semantics, 40–400 kg guard, latest-only patient edit, audit log; first weight captured at sign-up.
- Prescription delivery module: read Semble prescription + PDF (15-min URL → copy to our S3 or stream), pharmacy choice (whitelist), Healthmail email with attachment, SignatureRX NI issue + webhook status, one-send rule, admin reset, delivery log; 30-day €89 window.
- Join gates (questionnaire since 2026-08-24; payment gate with appointment-date grandfathering) with kill switches and fail-open.
- Point-of-sale acknowledgement record; duplicate-email refusal before charging; sales-assisted sign-up path (BE:`registerWithPayment.service.ts:489-572`).

**Must-not**
- Do not make the Semble patient ObjectId the login/PK, and do not link patients by name/email search.
- Do not derive access from Cognito group presence alone (the `community` skeleton-key class).
- Do not auto-import Stripe prices into a live catalog with empty role sets.
- Do not book via Semble API without passing `sendPatientMessages` deliberately, and do not assume Semble timestamps are UTC.
- Do not port the `patient_activities` ledger, `start_time` mutation, or the 19-table PK migration.
- Do not rely on Semble for Healthmail delivery until the "share a document to the clinic's own @healthmail.ie address" test has been run (MEM:`reference_adhd_semble_backend.md`).

**Decisions needed (client/Art)**
- MDT spacing: earliest-date windows (code) vs ±7-day targets (JM:322) vs book-all-upfront (MEM:`project_bbmi_90day_booking.md`: "pre-book all 8 on day one, not mandatory").
- Does the €89 funnel keep auto-booking the first consult (prod FE) or move to "pay → verify → questionnaire → book" (qa FE `79f60ab`)? This determines whether R25 ever binds for new patients.
- Turn the attendance payment gate on for prod (date), and whether a `payment_paused` member may attend.
- Video: Semble video vs Daily (recording → AI notes pipeline depends on Daily raw tracks, KB:`07:§7`).
- Questionnaires in Semble vs Tally-into-portal.
- Pharmacy directory location; Pure Pharmacy delivered-to-door flow; retire or re-home the McKeevers Lambda.
- Ongoing-care chooser (€150/€75) — prod has no `ONGOING_*` price ids configured.
- Which historical patients migrate to Semble (all ~10k vs active/recent).
