## TL;DR

1. **The eight slices are strong individually and agree on the spine** (portal owns identity + rules + Stripe; Semble owns the clinical record; every gate server-side; read model fed by webhooks). The gaps are at the seams: **nobody owns the staff/admin surface, the coexistence/cutover plan, the data-migration cohort, or the Semble tenant's actual state.**
2. **One hard factual contradiction was verified and is resolved in neither direction cleanly.** R02 says the €89 funnel *still* auto-books the first consult on prod; R01/R07 say *nothing* is booked at payment since 8 Sep. `git show origin/master` proves `planRequiresSlot()` returns `false` (FE `register-pay-page.component.ts:231-233`), so the in-app `/sign-up` path does not book — **but** the same file re-holds a slot whenever `?ref` arrives from a widget (`:339-343`), the backend saga still claims a slot when a token is present (BE `registerWithPayment.service.ts:583-591, 657-709`), and the live WordPress widget's default step order is still `cta -> slots -> …` "slot FIRST (Art, 2026-07-08)" with only `data-flow="enrol"` skipping it (WP `assets/widget/bbmi-assessment-widget.js:72-79, 206, 246-250`). **Auto-booking is entry-point dependent and no report says so.**
3. **Three further report-vs-report contradictions a designer would trip on:** `deleteBooking` soft (R04, measured) vs "hard delete" (R05, twice); `sendPatientMessages` default silent (R04, measured; scaffold comment) vs "defaults true, leave default" (R05); five-tab IA (R03) vs four-tab IA (R08).
4. **The Terms, the client journey map, the code and the scaffold disagree on at least ten patient-facing rules** (2 h vs 24 h notice; no-show policy; 25 vs 30 min consult; nurse vs Customer Support on Day 5–7; €89 access 30 days vs 1 year; €89 "clinical messaging" that does not exist; three different MDT-window models; community on €89; legacy role set 6 vs 8; instant cut-off vs 7/14-day grace). None of these has a single ratified answer, and the scaffold (`SCAF/lib/portal/programme.ts`) has silently picked a fourth model for the windows.
5. **The client's journey map assumes Semble does three things Semble cannot do** — patients/coordinators book MDT appointments "via Semble widget" (JM:320, 331), patients message the nurse "via async Semble support" (JM:789, 812, 1466), and "Semble flags no-show → HubSpot task" (JM:1459, 1575-1578). R04/R05 show the public widget must not be embedded, Semble has no inbound messaging, and Semble→HubSpot is not a committed integration. Nobody flagged this as a *client-communication* item.
6. **Unread sources that matter:** the Semble contract (Schedule 1) and `BBMI_Semble_Implementation_Scope_and_Call_Questions.md` are **not on this PC** (`Beyond BMI/Workspace/` holds only `retired-app-association-backup`; `find -iname "*semble*"` under Beyond BMI → nothing) — R05 calls it a "companion doc" but never opened it; `Index_4.html.html` (R07); the journey-map HTML; the Content Guideline PDFs (R03); the Duality repo (R06); the staff portal repo; the mobile-app KB (`04c_Mobile.md`). **ClickUp has zero Beyond BMI Semble tasks** (search "Semble" in ws `90152045381` → one ADHD task, `86cavbkku`), so the tenant's state (appointment system, region, webhooks, sandbox, token, products) is unknown to us ten days after the 1 Sep commencement date, and the contract's DocuSign status was last seen unsigned (memory `project_bbmi_semble_implementation.md`, 20 Jul).
7. **Prod facts asserted from memory, never read:** €89 no longer grants `community` (R07 states it as fact; R02 lists `community` in the €89 role set and flags the SQL as "status unknown"); legacy €150 = 6 vs 8 groups; `appoinment_intervals` ≈ 1 row; `patient_acknowledgements` DDL; the Stripe live dunning setting. All are one read-only DB/Stripe-dashboard query each.
8. **The scaffold already diverges from the research**: `programme.ts` encodes ±7-day-style fixed ranges (0–14 / 21–42 / 49–77), a 14-day pre-window, a `missed` state and a cross-role prerequisite (`nurse-m2 after doctor-m1`) that exist in no source; `types.ts` has `paymentIssue.graceEndsUtc` (no grace exists on prod, R07 §4) and labels Day 5–7/Day 80 as nurse calls (Index_4 reassigned both). It is also Next.js 16 (`package.json`), whereas R06's reusable lesson is "one standalone versioned API, many clients" — the framework/backend decision was never surfaced as a decision.
9. **Six decisions Art must take before the calendar, dashboard or auth screens are designed** (§6): backend shape (greenfield vs strangler on the Node monolith), identity/auth mode, the single booking-policy model, questionnaire hosting, video (Whereby vs Daily + AI-notes), and migration cohort + v1 scope boundary.
10. **Six gap-fill tasks** (§7), the first two of which block design: a Semble tenant/contract fact sheet (no token needed) and a per-entry-point funnel truth table.

## 4. Thin areas no slice covers

**A. Staff/admin operations the new design must re-home.** Today the Node backend + staff portal carry: mark completed / no-show (source of cooldowns and stages), prescription authoring (moves to Semble UI), doctor's questionnaire view filtered by a per-env form-id whitelist (memory `reference_bbmi_doctor_survey_view.md`), booking-eligibility overrides (`full_override`/`tier_reset`/`time_lock_reset`, R02 R24), admin prescription reset (R51), access codes/comps and ambassador provisioning (memory runbook), sales-assisted sign-up (BBMI-818, R07 §5.1), practice-side pause, support impersonation (`/sso-bridge`, R01 Q1), Cognito email change across four systems (R02 §8). R02 §9 says "overrides table + admin audit retained" and R02 §8 notes "the portal backend still needs a staff identity" — nothing specifies **which of these live in Semble's UI, which need a portal admin screen, and which Semble signal replaces each staff action** (`bookingJourney.completed`/`dna` vs a doctor pressing our button, R02 Q4).

**B. Coexistence and cutover.** The monolith at `bend.beyondbmi.ie` is today the endpoint for Stripe webhooks (entitlement + Cognito groups + HubSpot mirror), Tally webhooks (survey gate, first weight, GP), SendGrid bounce webhooks (prescription error flips), SignatureRX webhooks, the hourly McKeevers Lambda, the 6-hourly 90-day completion sweeper, reminder-email cron, and Cronofy calendars synced to clinicians' diaries. No report says what keeps running, in what order Cronofy is retired (clinician availability must exist in Semble first), how two backends avoid double-consuming Stripe events, or how the ~9 live 90-day members and ~970 active subscribers cross over without a stage flip. The retiring mobile app (`KB 04c`) is still a Cognito client hitting the same backend.

**C. Data migration cohort and identity backfill.** R02 §8 and R05 Q13 raise "which patients" and "who owns the mapping"; nobody proposes the answer or the dedupe strategy against Semble's own HubSpot import (`New HubSpot Import` label, R04 §2 identity row). Semble excludes migration (€3,000/dataset), the contract wants a HubSpot field for the Semble id, and the portal's mapping table (cognito_sub ↔ Semble ObjectId ↔ `numbers[System]` ↔ Stripe customer ↔ HubSpot email) is designed in three reports with slightly different column sets (R02 §8, R04 §3, R06 §3.3).

**D. Notifications ownership.** R05 §5 splits appointment comms (Semble) from lifecycle comms (build) but nobody lists today's email/SMS inventory (SendGrid from `support@`, reminder-email cleanup risk of 552 patients in memory `project_bbmi_team_discussion_jun24.md`, dead FCM push) or the ComReg sender-ID lead time for +353 SMS.

**E. Compliance.** R05 §6 (residency, SCCs), R06 §5.6 (Article 9), R08 §4 (EAA, HPRA, Medical Council) each raise items; there is no DPIA, no sub-processor register update (Semble, Whereby, SendGrid USA, Stripe, Sumsub, pharmacies), and no owner named.

**F. Testing without a sandbox.** R04 Q7: every API booking emails a real patient; R05 Q10 asks whether a sandbox is in the contract. Until answered, no E2E against Semble is possible and the "ready means verified e2e" rule (memory) cannot be met.

**G. v1 scope boundary.** R08 proposes a treatment loop (dose card, site map, missed-dose rules, side-effect check-ins, dose-review requests) that the JM promises only as "medication tracking" (R07 §1.2) and that needs Dr Alvin's sign-off (R08 Q2) and an HPRA opinion (R08 Q6). ## 6. Architecture decisions Art must make (with evidence)

**D1 — Backend shape: greenfield portal backend (Next.js server / new service) vs strangler on the existing Node monolith.**
For greenfield: Node 18/Angular 14 EOL (memory handover); three eligibility implementations, one failing open (R02 §5); non-idempotent webhooks, Cognito groups as side effects, 19-table PK migration, duplicate `stripe_subscription_id` rows (R02 §5, §8); master 876 commits behind qa with dead migrations (memory release process); R06's adapter-seam architecture wants a clean domain package. For strangler: the rules that matter are already E2E-proven on prod as of 8 Sep — nine-stage machine, 72 h grace, `billingIssue`, 90-day windows/allocation, duplicate-email guard, acknowledgements, HubSpot property contract (R07 §6 table); Stripe, HubSpot, SendGrid, SignatureRX, Sumsub integrations are live; R02 §7 recommends "reproduce" not "reuse".
